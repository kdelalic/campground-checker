# Architecture

The project is a thin wrapper around the [camply](https://github.com/juftin/camply) library, with a native Recreation.gov client of its own. The entry point is `check_campsites.py`, which delegates to `campsite_checker/runner.py:main()`.

## Module responsibilities

### Configuration and providers

- `campsite_checker/config.py` — CLI argument parsing (`parse_args`), YAML config loading (`load_config`), date range computation, day-of-week filter resolution. Supports two YAML formats: provider-keyed dict (new) and flat list with optional `provider` field (legacy).
- `campsite_checker/weekdays.py` — Weekday name → `datetime.weekday()` integer mapping and its inverse labels.
- `campsite_checker/providers/__init__.py` — Registry only: maps provider name strings (`RecreationDotGov`, `Yellowstone`, `GoingToCamp`, `ReserveCalifornia`) to search classes via `PROVIDER_MAP`, plus `METADATA_PROVIDER_CLASS` for the bot's out-of-search name lookups and `PROVIDER_DISPLAY` for labels. Adding a provider means adding an entry here and, if it needs subclassing, a sibling module for it.
- `campsite_checker/providers/recreation_gov.py` — Native Recreation.gov availability client (`NativeSearchRecreationDotGov`), replacing camply's search path. Holds `FACILITY_IDENTITY_CACHE` (24h TTL, LRU-bounded) so resolved `CampgroundFacility` identities survive across searcher construction, eliminating one RIDB round trip per campground per scan (~1s each); failed or filtered lookups are never cached. Also owns `RequestGate` (process-wide rate limiting) and `PROVIDER_REQUEST_METRICS`.
- `campsite_checker/providers/reserve_california.py` — `TimeoutReserveCalifornia`: stock camply UseDirect HTTP calls have no timeout, so a black-holed connection would hang a scan thread forever; this applies `DEFAULT_HTTP_TIMEOUT_SECONDS` (30s) to every request. It also relocates camply's UseDirect offline metadata cache from its site-packages default (unwritable by the unprivileged container user) to `CAMPLY_CACHE_DIR` (default `.camply-cache/`; the image sets `/app/state/camply-cache`).

### Search execution

- `campsite_checker/dispatch.py` — Process-wide `SearchDispatcher` shared by alert and dashboard scans. `--workers` bounds concurrently executing search batches across the whole process; queued alert work is dispatched ahead of queued dashboard work; dashboard work is capped at `workers - 1` concurrent batches (with `workers=1` the single slot is shared: a dashboard batch may occupy it and alert work runs next as soon as it finishes); a dashboard batch that has waited longer than `DASHBOARD_PROMOTION_SECONDS` (60s) is ordered like alert work so sustained alert load cannot starve dashboard scans. `--search-delay` pacing is tracked per provider inside the dispatcher, so overlapping scans share one submission schedule, and provider cooldowns are checked at dispatch time, so a newly activated cooldown fails queued work from both scan types fast (`ProviderCooldownActive`). The module-level dispatcher is created lazily by `execute_searches` and shut down via `shutdown_dispatcher` when the runner exits.
- `campsite_checker/search.py` — Builds camply searcher objects from config entries (`build_searcher`) and runs bounded search batches through the process-wide dispatcher (`execute_searches`). Handles a provider-specific quirk: `ReserveCalifornia` requires a `recreation_area` positional arg even when only `campground_id` is given, so an empty list is passed in that case.
- `campsite_checker/throttle.py` — Detects provider HTTP 429 responses, including exceptions wrapped by retry libraries, and maintains process-wide provider cooldowns. Backoff starts at `THROTTLE_BASE_DELAY`, doubles on consecutive limits, honors longer `Retry-After` values, and caps the computed exponential delay at `THROTTLE_MAX_DELAY`. Queued work for a throttled provider is skipped until a later scan while other providers continue.
- `campsite_checker/results.py` — Post-search filtering: excludes boat/hike-in sites, applies day-of-week filter, formats terminal output. Defines `NotificationKey` and the availability fingerprint used to decide whether the dashboard needs rewriting.

### Output

- `campsite_checker/notify.py` — Telegram notification logic: credential resolution (CLI > env vars > YAML), dedup filtering via `filter_new_availability`, per-campground alert filtering, sends HTML-formatted messages via Telegram Bot API. `send_telegram` returns delivery success so the runner can defer the dedup checkpoint when a send fails (the alert is retried next scan instead of being lost).
- `campsite_checker/state.py` — On-disk persistence for the Telegram dedup keys (`SENT_KEYS_PATH`, default `.campsite_sent_keys.json`). Writes atomically via temp file + rename, prunes past booking dates on both load and save, and returns whether anything actually changed so unchanged state is not rewritten.
- `campsite_checker/bot.py` — Telegram bot command handlers (`/list`, `/alert`, `/status`, `/help`). Read-only: the bot reports what is being monitored but never edits `campsites.yaml`. `ConfigState` holds thread-safe shared state (entries, raw config, config path); the lock is held only for in-memory reads, with network calls made outside it. Only active in `--forever` mode when Telegram credentials are set.
- `campsite_checker/dashboard.py` — Static HTML dashboard generation. Builds view models (`CardView`, `DateRowView`, `CalendarMonth`, `StatsView`) from `ProcessedAvailability` and renders `templates/dashboard.html.j2` with Jinja2. Autoescaping is on, so dynamic values must **not** be pre-escaped with `html.escape`; markup that is intentionally raw (the inlined CSS/JS) is passed through `|safe`. Entries whose search failed (`ProcessedAvailability.search_succeeded=False`) render as an amber "Scan failed" card rather than as "No availability", so a provider cooldown is never mistaken for an empty campground; the fingerprint in `results.py` includes `search_succeeded` so a failure→success transition rewrites the page. Each date row is a `<details>` disclosure listing individual sites with per-site booking links, and the page reloads itself every `DEFAULT_REFRESH_SECONDS` (300) while the tab is visible.
- `campsite_checker/templates/` — Dashboard assets: `dashboard.html.j2` (Jinja2 page template), `dashboard.css`, and `dashboard.js`. The CSS and JS are plain static files read via `importlib.resources` (`read_asset`, cached) and inlined into the rendered page, so the output stays a single self-contained file while the sources remain lintable and syntax-highlighted. `dashboard.js` must stay template-free — runtime values reach it through data attributes on the markup (e.g. `data-refresh-seconds`). There is deliberately no frontend build step or Node toolchain: the page is a server-rendered read-only report, and everything except the date filter works with JS disabled.
- `campsite_checker/upload.py` — Optional Cloudflare R2 upload for the dashboard. Uses boto3 S3-compatible API. Credentials resolved via env vars or YAML `dashboard.r2` section.
- `campsite_checker/yaml_comments.py` — Read-only YAML comment parsing via `ruamel.yaml`. `parse_yaml_comments` recovers campground names from the inline comments in `campsites.yaml` for `bot.py` and `config.py`. It deliberately has no mutating helpers: `campsites.yaml` is git-managed and mounted read-only, so nothing may write it at runtime.

### Observability

See [observability.md](observability.md) for the metric reference.

- `campsite_checker/status.py` — `ScanStatus`, the single mutable observability object. The runner writes scan counters, availability gauges, notification counts, and dashboard-worker lifecycle into it; readers get either `to_dict()` (health JSON) or `snapshot()` (an immutable `MetricsSnapshot` for rendering). All access is lock-guarded.
- `campsite_checker/metrics.py` — Prometheus text-exposition rendering and `CampgroundMetric` (the per-campground label set). Owns metric names and help strings; holds no state.
- `campsite_checker/server.py` — The HTTP server itself: `/` for health JSON (503 when scans are stale) and `/metrics` for the Prometheus exposition. Threaded so one slow client cannot block probes. Runs on `PORT` (default 8000). No filesystem access and no other routes.
- `grafana/campground-checker.json` — Canonical provisioned Grafana dashboard. The deploy workflow copies it into the homelab monitoring stack; update it in the same change as any metric rename or removal.

### Orchestration

- `campsite_checker/runner.py` — Orchestrates single-run (`run_once`) and polling loop (`run_forever`). In `--forever` mode, uses two-tier scanning: entries with `alert: true` are searched every `--alert-interval` minutes (CLI default 5; container default 1), while dashboard-only entries are searched every `--dashboard-interval` minutes (CLI default 60; container default 10; configurable via CLI, `dashboard.interval` YAML key, or `DASHBOARD_INTERVAL` env var). Alert scans, notifications, and their dedup checkpoint run in the foreground. Dashboard-only scans run in one non-overlapping background worker, and their completed results are merged into the next foreground cycle without blocking the alert deadline. Individual scan failures are caught and logged without stopping the loop.

## Key design decisions

- Compatible campground searches are grouped into bounded batches; batches from all overlapping scans run concurrently under one process-wide worker limit with global per-provider submission pacing (see `dispatch.py`).
- Telegram deduplication in `--forever` mode: a key is `(provider, entry_identity, campsite_id, booking_date)`, where `entry_identity` is the configured campground/recreation-area ID — a provider-side facility rename cannot re-trigger or suppress alerts. Keys are persisted atomically to disk, kept for the full search horizon, and pruned of past dates. Keys are only checkpointed after all Telegram messages for the cycle were delivered, so a failed send is retried next scan.
- Day-of-week filtering (default: Sunday only) is applied in post-processing, not in the camply search itself.
- Telegram credential priority: CLI flags > `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID` env vars > `telegram.bot_token`/`telegram.chat_id` in YAML config.
- Per-campground alerts: per-entry `alert: true` enables Telegram notifications for that campground (default: off). Terminal output and dashboard still show all sites. Change it by editing `campsites.yaml` and pushing; `/alert` in the bot displays current state but cannot change it.
- `campsites.yaml` is the source of truth and lives in git. The deployment mounts it read-only and every deploy resets the working tree, so runtime edits would not survive regardless.
- Dashboard: `--dashboard` flag or `dashboard.output_path` in YAML generates a static HTML file after each scan. Optional R2 upload via `dashboard.r2` config or `R2_ACCOUNT_ID`/`R2_ACCESS_KEY_ID`/`R2_SECRET_ACCESS_KEY`/`R2_BUCKET_NAME`/`R2_OBJECT_KEY`/`R2_CUSTOM_DOMAIN` env vars. `boto3` is required only for R2 upload (lazy import).
