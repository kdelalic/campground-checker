# Architecture

The project is a thin wrapper around the [camply](https://github.com/juftin/camply) library, with a native Recreation.gov client of its own. The entry point is `check_campsites.py`, which delegates to `campsite_checker/runner.py:main()`.

## Module responsibilities

### Configuration and providers

- `campsite_checker/config.py` — CLI argument parsing (`parse_args`), YAML config loading (`load_config`), date range computation, day-of-week filter resolution. Supports two YAML formats: provider-keyed dict (new) and flat list with optional `provider` field (legacy).
- `campsite_checker/weekdays.py` — Weekday name → `datetime.weekday()` integer mapping and its inverse labels.
- `campsite_checker/providers/__init__.py` — Registry only: maps provider name strings (`RecreationDotGov`, `Yellowstone`, `GoingToCamp`, `ReserveCalifornia`) to search classes via `PROVIDER_MAP`, plus `METADATA_PROVIDER_CLASS` for the bot's out-of-search name lookups and `PROVIDER_DISPLAY` for labels. Adding a provider means adding an entry here and, if it needs subclassing, a sibling module for it.
- `campsite_checker/request_gate.py` — `RequestGate`, the process-wide gate each provider uses to order its outbound requests. Waiters are queued by `(priority, arrival)` — lower wins — so a queued alert request takes the next available start even when dashboard requests have been waiting longer, and one concurrency slot is held back for alert requests (`deprioritized_slots`), mirroring the dispatcher's reserved worker. Ordering alone proved insufficient in production: without a reserved slot an alert still waits for an in-flight dashboard request to finish, which on a seconds-per-request provider cost ~30s across a 7-request alert scan. The dispatcher orders *batches* this way; the gate applies the same rules to the individual requests inside a batch, which is what keeps an alert fast while a long dashboard sweep is mid-flight. Priority reaches a searcher as `request_priority`, forwarded by `search.build_searcher` only to constructors that declare it. The gate also caps concurrency, optionally spaces starts (`requests_per_second`), and exposes `defer(seconds)` plus `pause_gate_on_rate_limit` to pause every future start after a 429. An in-flight request is never preempted, so with `max_concurrent=1` an alert may still wait out the one outstanding request, bounded by that provider's timeouts. Each provider owns its own instance because the limits being respected are per-provider. The module also owns `PROVIDER_REQUEST_METRICS` (`ProviderRequestMetrics`), the per-provider attempt/retry/failure counters every native client records into and `metrics.py` renders — it lives beside the gate rather than inside one provider's module because both native clients share it.
- `campsite_checker/providers/recreation_gov.py` — Native Recreation.gov availability client (`NativeSearchRecreationDotGov`), replacing camply's search path. Holds `FACILITY_IDENTITY_CACHE` (24h TTL, LRU-bounded) so resolved `CampgroundFacility` identities survive across searcher construction, eliminating one RIDB round trip per campground per scan (~1s each); failed or filtered lookups are never cached. Also owns `REC_GOV_REQUEST_GATE`, a `request_gate.RequestGate` configured to 1 request/second with at most 2 in flight. On HTTP 429 the client defers that gate (`Retry-After`, else 30s) while still holding its slot, so batches already executing stop issuing requests immediately instead of each discovering the limit itself. It then *retries* the rate-limited request rather than failing it: re-acquiring the gate slot is what waits the pause out, so the backoff is the provider's own and no local delay is slept on top of it. Alert requests get one such retry and dashboard requests two (`ALERT_MAX_RATE_LIMIT_RETRIES` / `DEFAULT_MAX_RATE_LIMIT_RETRIES`), keeping a rate-limited alert scan inside its interval. Because a successful retry raises nothing, the batch never reports `rate_limited` and no provider cooldown is registered — only sustained rate limiting, where the retries are exhausted, escalates to the cooldown path.
- `campsite_checker/providers/reserve_california.py` — Native ReserveCalifornia (UseDirect) availability client (`NativeSearchReserveCalifornia`), replacing camply's `SearchReserveCalifornia`. The decisive reason is correctness: the UseDirect grid endpoint silently caps every response at 21 days of slices whatever `EndDate` asks for, and camply's search loops over *calendar months*, so days 22..EOM were never checked for any campground. This client slices the search window into `MAX_GRID_WINDOW_DAYS` (21) requests instead, sized against the days a stay actually needs — with `nights > 1` under `weekends_only` the trailing nights are not themselves search days — and joins availability across windows so a stay spanning a window boundary is still found. Dropping camply's search path also drops its 100-minute `tenacity` retry window (`RETRY_MAX_API_TIMEOUT`), which nothing above it bounded (`search.execute_searches` calls `future.result()` without a timeout), and its process-global `@ratelimit.limits(calls=1, period=1)` on the availability call, which serialised all UseDirect traffic behind an unfair lock and so defeated the gate's alert-first ordering downstream of it. Retries are bounded exactly as in the Recreation.gov client (3 attempts; 429 defers the gate and is retried once for alerts, twice for dashboard scans). `RESERVE_CALIFORNIA_REQUEST_GATE` allows at most 3 requests in flight (2 usable by dashboard scans, one reserved for alerts), alert-first, paced at `REQUESTS_PER_SECOND` (4) — deliberately looser than camply's 1/s, but retained so removing that decorator does not become an unbounded increase in request rate. Full coverage costs ~30% more requests than the truncated month loop it replaces (a 6-month window is 9 windows per campground rather than 7 months), which the absence of any known ReserveCalifornia rate limit affords.
  `TimeoutReserveCalifornia` remains for facility identity and unit-category metadata, which the native client builds on: stock camply UseDirect HTTP calls have no timeout, so a black-holed connection would hang a scan thread forever; this applies `DEFAULT_HTTP_TIMEOUT_SECONDS` (30s) to every request. It also relocates camply's UseDirect offline metadata cache from its site-packages default (unwritable by the unprivileged container user) to `CAMPLY_CACHE_DIR` (default `.camply-cache/`; the image sets `/app/state/camply-cache`), and `refresh_stale_metadata` re-fetches that cache once it passes `METADATA_MAX_AGE_SECONDS` (24h, camply's own TTL). Camply expires the cache only when `active_search` is False, but `find_campgrounds` sets it True *before* refreshing, so on every path this project uses the expiry never fired — and since `CAMPLY_CACHE_DIR` is a persistent volume, the metadata stayed frozen at whatever the first run downloaded: campgrounds newly opened by ReserveCalifornia stayed unfindable and renamed parks kept their old names indefinitely. A module-level lock serialises the re-fetch so concurrent searches that all notice the same stale cache do not each re-download it. Those requests share the same gate, at the priority of the scan that triggered them: the provider is built before any per-request argument exists, so `provider_class_for_priority` carries the priority on the class itself.

### Search execution

- `campsite_checker/dispatch.py` — Process-wide `SearchDispatcher` shared by alert and dashboard scans. `--workers` bounds concurrently executing search batches across the whole process; queued work is selected strictly by `(priority, sequence)`, so alert work always outranks queued dashboard work no matter how long the dashboard batch has waited (there is no promotion rule — alerts are the latency-sensitive path); dashboard work is capped at `workers - 1` concurrent batches (with `workers=1` the single slot is shared: a dashboard batch may occupy it and alert work runs next as soon as it finishes), which is what keeps dashboard scans progressing. `--search-delay` pacing is tracked per provider inside the dispatcher, so overlapping scans share one submission schedule, and provider cooldowns are checked at dispatch time. A newly activated cooldown fails queued *alert* work fast (`ProviderCooldownActive`), since that scan re-runs within its interval; queued *dashboard* work instead waits the cooldown out when it is no longer than `max_cooldown_wait` (`DEFAULT_MAX_COOLDOWN_WAIT_SECONDS`, 60s), because failing it strands every campground in the batch until the next dashboard interval — a far bigger coverage loss than the pause. Cooldowns above that budget fail dashboard work too, so a genuine provider outage does not stall scans behind it. The module-level dispatcher is created lazily by `execute_searches` and shut down via `shutdown_dispatcher` when the runner exits.
- `campsite_checker/search.py` — Builds searcher objects from config entries (`build_searcher`) and runs bounded search batches through the process-wide dispatcher (`execute_searches`). Handles a provider-specific quirk: camply's `SearchGoingToCamp` requires a `recreation_area` positional arg even when only `campground_id` is given, so an empty list is passed in that case.
- `campsite_checker/throttle.py` — Detects provider HTTP 429 responses, including exceptions wrapped by retry libraries, and maintains process-wide provider cooldowns. Backoff starts at `THROTTLE_BASE_DELAY`, doubles on consecutive limits, honors longer `Retry-After` values, and caps the computed exponential delay at `THROTTLE_MAX_DELAY`. Queued alert work for a throttled provider is skipped until a later scan while other providers continue; dashboard work waits out short cooldowns instead (see `dispatch.py`).
- `campsite_checker/results.py` — Post-search filtering: excludes boat/hike-in sites, applies day-of-week filter, formats terminal output. Defines `NotificationKey` and the availability fingerprint used to decide whether the dashboard needs rewriting.

### Output

- `campsite_checker/notify.py` — Telegram notification logic: credential resolution (CLI > env vars > YAML), dedup filtering via `filter_new_availability`, per-campground alert filtering, sends HTML-formatted messages via Telegram Bot API. `send_telegram` returns delivery success so the runner can defer the dedup checkpoint when a send fails (the alert is retried next scan instead of being lost).
- `campsite_checker/state.py` — On-disk persistence for the Telegram dedup keys (`SENT_KEYS_PATH`, default `.campsite_sent_keys.json`). Writes atomically via temp file + rename, prunes past booking dates on both load and save, and returns whether anything actually changed so unchanged state is not rewritten.
- `campsite_checker/bot.py` — Telegram bot command handlers (`/list`, `/alert`, `/status`, `/help`). Read-only: the bot reports what is being monitored but never edits `campsites.yaml`. `ConfigState` holds thread-safe shared state (entries, raw config, config path); the lock is held only for in-memory reads, with network calls made outside it. Only active in `--forever` mode when Telegram credentials are set.
- `campsite_checker/dashboard.py` — Static HTML dashboard generation. Builds view models (`CardView`, `DateRowView`, `CalendarMonth`, `StatsView`) from `ProcessedAvailability` and renders `templates/dashboard.html.j2` with Jinja2. Autoescaping is on, so dynamic values must **not** be pre-escaped with `html.escape`; markup that is intentionally raw (the inlined CSS/JS) is passed through `|safe`. Entries whose search failed (`ProcessedAvailability.search_succeeded=False`) render as an amber "Scan failed" card rather than as "No availability", so a provider cooldown is never mistaken for an empty campground; the fingerprint in `results.py` includes `search_succeeded` so a failure→success transition rewrites the page. `DashboardPublisher` retains the most recent successful result for each campground in memory and substitutes it, clearly labeled as a stale snapshot, when a later scan fails completely. Those retained rows remain bookable inside the failed card but are never counted as current availability or painted green in the calendar. Configured latitude/longitude values produce one map marker per campground even for empty or failed scans; a provider result location is the fallback. Each date row is a `<details>` disclosure listing individual sites with per-site booking links, and the page reloads itself every `DEFAULT_REFRESH_SECONDS` (300) while the tab is visible. The date, month, text search, and status filter are kept in the URL so that reload restores the reader's view. The header carries a `SearchFilterView` (`build_search_filter_view`) naming the days, stay length, and date range the scan ran with; the same structured start/end range drives a calendar that always spans the complete search window, even when no availability was found. Stay length appears twice on purpose: the header summarises every entry on the page (`format_nights`, rendering `1 / 3 nights` when they disagree), while each card carries its own exact value from `build_nights_label`, since one entry with `criteria` searches several lengths at once. Both read the `_searched_nights` values that `runner.run_once` stamps on each entry, because neither the `--nights` override nor a `criteria` block is visible from an entry's own `nights` key; the header summarises the *rendered* availabilities rather than the config, so it can never disagree with the cards below it. `DashboardPublisher.publish` mixes `SearchFilterView.fingerprint` into the availability fingerprint so a relative window rolling forward republishes the page even when availability is unchanged. `build_dashboard_cards` orders cards by `card_sort_key` — campgrounds with current availability first, ranked by site/date opening count, then failed scans (including stale snapshots), then confirmed empties, with name breaking ties so the order is stable. Confirmed-empty cards are collapsed by default to keep the actionable results short.
- `campsite_checker/templates/` — Dashboard assets: `dashboard.html.j2` (Jinja2 page template), `dashboard.css`, and `dashboard.js`. The CSS and JS are plain static files read via `importlib.resources` (`read_asset`, cached) and inlined into the rendered page, so the output stays a single HTML artifact while the sources remain lintable and syntax-highlighted. The vendored MapLibre runtime and CSS under `templates/vendor/` are also inlined; only live OpenFreeMap style, tile, glyph, and sprite resources are external requests. `dashboard.js` must stay template-free — runtime values reach it through data attributes on the markup (e.g. `data-refresh-seconds`, `data-label` on calendar cells, and the accessible map-marker data list). There is deliberately no frontend build step or Node toolchain: the page is a server-rendered read-only report, and essential availability data remains available with JS disabled. Visual and content changes follow the [dashboard style guide](dashboard-style-guide.md).
- `campsite_checker/upload.py` — Optional Cloudflare R2 upload for the dashboard. Uses boto3 S3-compatible API. Credentials resolved via env vars or YAML `dashboard.r2` section.
- `campsite_checker/yaml_comments.py` — Read-only YAML comment parsing via `ruamel.yaml`. `parse_yaml_comments` recovers campground names from the inline comments in `campsites.yaml` for `bot.py` and `config.py`. It deliberately has no mutating helpers: `campsites.yaml` is git-managed and mounted read-only, so nothing may write it at runtime.

### Observability

See [observability.md](observability.md) for the metric reference.

- `campsite_checker/status.py` — `ScanStatus`, the single mutable observability object. The runner writes scan counters, availability gauges, notification counts, and dashboard-worker lifecycle into it; readers get either `to_dict()` (health JSON) or `snapshot()` (an immutable `MetricsSnapshot` for rendering). All access is lock-guarded.
- `campsite_checker/metrics.py` — Prometheus text-exposition rendering and `CampgroundMetric` (the per-campground label set). Owns metric names and help strings; holds no state.
- `campsite_checker/server.py` — The HTTP server itself: `/` for health JSON (503 when scans are stale) and `/metrics` for the Prometheus exposition. Threaded so one slow client cannot block probes. Runs on `PORT` (default 8000). No filesystem access and no other routes.
- `grafana/campground-checker.json` — Canonical provisioned Grafana dashboard. The deploy workflow copies it into the homelab monitoring stack; update it in the same change as any metric rename or removal.

### Orchestration

- `campsite_checker/runner.py` — Orchestrates single-run (`run_once`) and polling loop (`run_forever`). In `--forever` mode, uses two-tier scanning: entries with `alert: true` are searched every `--alert-interval` minutes (CLI default 5; container default 1), while dashboard-only entries are searched every `--dashboard-interval` minutes (CLI default 60; container default 10; configurable via CLI, `dashboard.interval` YAML key, or `DASHBOARD_INTERVAL` env var). Alert scans, notifications, and their dedup checkpoint run in the foreground. Dashboard-only scans run in one non-overlapping background worker, and their completed results are merged into the next foreground cycle without blocking the alert deadline. A sweep that outruns its own interval would otherwise be due the instant it finishes, running sweeps back to back and raising the request rate exactly when the provider is most likely throttling, so the next sweep also waits `MIN_DASHBOARD_IDLE_SECONDS` (60s) after the previous one completes. Individual scan failures are caught and logged without stopping the loop.

## Key design decisions

- Compatible campground searches are grouped into bounded batches; batches from all overlapping scans run concurrently under one process-wide worker limit with global per-provider submission pacing (see `dispatch.py`).
- Telegram deduplication in `--forever` mode: a key is `(provider, entry_identity, campsite_id, booking_date)`, where `entry_identity` is the configured campground/recreation-area ID — a provider-side facility rename cannot re-trigger or suppress alerts. Keys are persisted atomically to disk, kept for the full search horizon, and pruned of past dates. Keys are only checkpointed after all Telegram messages for the cycle were delivered, so a failed send is retried next scan.
- Day-of-week filtering (default: Sunday only) is applied in post-processing, not in the camply search itself.
- Telegram credential priority: CLI flags > `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID` env vars > `telegram.bot_token`/`telegram.chat_id` in YAML config.
- Per-campground alerts: per-entry `alert: true` enables Telegram notifications for that campground (default: off). Terminal output and dashboard still show all sites. Change it by editing `campsites.yaml` and pushing; `/alert` in the bot displays current state but cannot change it.
- `campsites.yaml` is the source of truth and lives in git. The deployment mounts it read-only and every deploy resets the working tree, so runtime edits would not survive regardless.
- Dashboard: `--dashboard` flag or `dashboard.output_path` in YAML generates a static HTML file after each scan. Optional R2 upload via `dashboard.r2` config or `R2_ACCOUNT_ID`/`R2_ACCESS_KEY_ID`/`R2_SECRET_ACCESS_KEY`/`R2_BUCKET_NAME`/`R2_OBJECT_KEY`/`R2_CUSTOM_DOMAIN` env vars. `boto3` is required only for R2 upload (lazy import).
